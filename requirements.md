## 1. Введение

### 1.1 Назначение документа
Документ определяет функциональные, технические, архитектурные и эксплуатационные
требования к информационной системе «Женское такси». Он является основным
источником требований для всех участников проекта:

- владелец продукта;
- аналитики;
- UX/UI-дизайнеры;
- мобильные разработчики;
- backend-разработчики;
- DevOps-инженеры;
- QA-инженеры;
- специалисты по информационной безопасности.

Все изменения в проекте должны производиться с учётом требований настоящего документа.

### 1.2 Область применения
Система — специализированная цифровая платформа заказа такси для женщин и семей,
где перевозки выполняются **исключительно женщинами-водителями**.

## 2. Концепция проекта

### 2.1 Цель
Создать современную цифровую платформу заказа такси для женщин и семей с перевозками
исключительно женщинами-водителями. Платформа должна обеспечивать:

- безопасность;
- комфорт;
- прозрачность стоимости поездки;
- простоту использования;
- высокую скорость поиска автомобиля;
- возможность масштабирования на любые регионы.

### 2.2 Основная идея
Проект создаётся не как очередной агрегатор такси, а как **специализированная
экосистема безопасных перевозок**. Ключевые принципы:

- женщина-клиент взаимодействует только с женщиной-водителем;
- все водители проходят обязательную верификацию;
- стоимость поездки известна до оформления заказа;
- маршрут полностью отслеживается;
- родственники могут контролировать поездку через совместный доступ;
- каждая поездка хранится в истории;
- предусмотрены механизмы экстренной помощи (SOS).

### 2.3 Миссия
Обеспечить женщинам Северного Кавказа безопасный, удобный и современный способ
передвижения, соответствующий культурным особенностям региона.

### 2.4 Видение
Стать крупнейшим специализированным сервисом женских перевозок на Северном Кавказе
с возможностью выхода в другие регионы РФ и, при необходимости, в другие страны с
аналогичным спросом.

### 2.5 Ключевые ценности
1. Безопасность.
2. Доверие.
3. Прозрачность.
4. Скорость.
5. Масштабируемость.

Все решения по разработке должны соответствовать этим принципам.

## 6. Архитектура системы

### 6.1 Компоненты платформы
Система — единая платформа из независимых, слабосвязанных компонентов, обменивающихся
данными через API и события:

1. Мобильное приложение клиента.
2. Мобильное приложение водителя.
3. Веб-панель администратора.
4. Веб-панель супер-администратора.
5. Backend API.
6. Сервис WebSocket (реальное время).
7. Сервис уведомлений.
8. Сервис геолокации и маршрутизации.
9. Платёжный сервис.
10. Сервис аналитики и мониторинга.

### 6.2 Принципы проектирования
- модульная архитектура;
- отказоустойчивость;
- минимальная связанность модулей;
- высокая производительность;
- безопасность по умолчанию (Security by Design);
- масштабируемость;
- наблюдаемость (Observability);
- независимое обновление компонентов.

### 6.3 Требования к масштабируемости
Архитектура должна позволять **без изменения исходного кода**:
- добавлять новые регионы;
- подключать новые города через административную панель;
- создавать собственные тарифы для каждого региона;
- назначать региональных администраторов;
- изменять комиссии независимо по регионам;
- включать/отключать отдельные функции по регионам;
- использовать разные платёжные системы по регионам;
- использовать разных SMS-провайдеров;
- поддерживать нескольких поставщиков карт и маршрутизации;
- масштабироваться горизонтально.

## 7. Роли пользователей и права доступа

### 7.1 Клиент
Регистрация; авторизация; редактирование профиля; заказ поездок; просмотр истории;
сохранение адресов; просмотр стоимости до оформления; оплата; отмена поездок; оценка
водителя; обращение в поддержку; функция SOS; приглашение друзей; использование промокодов.

### 7.2 Водитель
Регистрация; прохождение проверки документов; загрузка документов; изменение статуса
«На линии»; получение и принятие заказов; построение маршрута; просмотр доходов; вывод
средств; просмотр рейтинга; просмотр истории заказов; обращение в поддержку.

### 7.3 Оператор
Просмотр заказов; помощь клиентам и водителям; изменение статусов заказов; ручное
назначение водителя; создание компенсаций; оформление возвратов.

### 7.4 Региональный администратор
Доступ **только к своему региону**: управление водителями; подтверждение документов;
управление тарифами; просмотр статистики; блокировка пользователей; работа с обращениями.

### 7.5 Супер-администратор
Полный доступ ко всей системе: создание регионов и городов; изменение комиссий и тарифов;
создание администраторов; назначение прав; подключение новых платёжных систем и карт;
управление всеми данными.

## 8. Функциональные требования

### 8.1 Регистрация клиента
Регистрация не должна занимать более одной минуты. Последовательность:

1. Ввод номера телефона.
2. Отправка SMS-кода.
3. Подтверждение кода.
4. Создание пользователя.
5. Запрос имени.
6. (Опционально) Добавление фотографии.
7. Согласие на обработку персональных данных.
8. Переход на главный экран.

### 8.2 Регистрация водителя
**Этап 1. Создание аккаунта.**

**Этап 2. Заполнение анкеты** — обязательные поля:
- ФИО;
- дата рождения;
- номер телефона;
- адрес проживания;
- стаж вождения;
- регион работы.

**Этап 3. Загрузка документов** (обязательно):
- паспорт;
- водительское удостоверение;
- СТС;
- полис ОСАГО;
- фотография автомобиля;
- фотография салона;
- селфи для подтверждения личности.

**Этап 4. Проверка документов** — автоматически (OCR + AI в будущем) или вручную
модератором. До прохождения проверки водитель **не может** принимать заказы.

### 8.3 Профиль клиента
Фотография; имя; номер телефона; язык интерфейса; способы оплаты; история поездок;
бонусный баланс; промокоды; любимые адреса; избранные водители; экстренные контакты;
настройки уведомлений; настройки приватности.

### 8.4 Профиль водителя
Фотография; рейтинг; количество поездок; доход за день/неделю/месяц; статус проверки
документов; сведения об автомобиле; график работы; статистика.

### 8.5 Любимые адреса
Пользователь может сохранить: Дом; Работа; Родители; Университет; Школа; Детский сад;
любой собственный адрес. **Количество адресов не ограничено.**

### 8.6 Семейный аккаунт
Клиент может добавить членов семьи (маму, дочь, супругу, сестру). После подтверждения:
- заказать поездку другому человеку;
- отслеживать поездку;
- получать уведомления;
- оплачивать поездку со своего счёта.

### 8.7 Экстренные контакты и SOS
Клиент может добавить **до пяти** доверенных контактов. При активации SOS выбранным
контактам автоматически отправляются:
- ссылка на маршрут;
- текущие координаты;
- информация о водителе;
- информация об автомобиле;
- статус поездки.

### 8.8 Главный экран клиента
Карта; поле поиска адреса; кнопка текущего местоположения; список сохранённых адресов;
кнопка заказа; стоимость поездки; предполагаемое время подачи автомобиля; выбор тарифа;
меню профиля.

### 8.9 Поиск адресов
Поддержка поиска по: адресам; улицам; домам; организациям; ориентирам; координатам.
Система должна учитывать региональные особенности адресации населённых пунктов Северного
Кавказа и корректно обрабатывать различные варианты написания названий.

### 8.10 Заказ поездки
1. Выбор точки отправления.
2. Выбор пункта назначения.
3. Расчёт маршрута.
4. Расчёт стоимости.
5. Выбор тарифа.
6. Выбор способа оплаты.
7. Возможность оставить комментарий.
8. Подтверждение заказа.
9. Поиск свободного водителя.
10. Назначение водителя.
11. Отображение автомобиля на карте.

### 8.11 Комментарии к заказу
Клиент может оставить комментарий (например: «Заехать во двор», «Буду у второго
подъезда», «Со мной ребёнок», «Позвоните по прибытии», «Есть багаж»). Комментарий
отображается водителю сразу после принятия заказа.

### 8.12 Отмена заказа
Сценарии: отмена до назначения водителя; после назначения; после прибытия водителя;
во время поездки (только в исключительных случаях). Правила возврата средств и штрафы
определяются тарифной политикой региона и настраиваются через админ-панель **без
изменения кода**.

### 8.13 История поездок
Для каждой поездки сохраняются: дата; время; стоимость; маршрут; водитель; автомобиль;
способ оплаты; рейтинг; чек; статус поездки; электронная квитанция.
История хранится **бессрочно**, если иное не предусмотрено законодательством.

### 8.14 Система отзывов
После завершения поездки клиент может: поставить оценку от 1 до 5; оставить текстовый
отзыв; отметить преимущества (вежливость, чистота автомобиля, аккуратное вождение);
сообщить о проблеме. Водитель также может оценить клиента. Оценки используются внутренней
системой доверия и **не** ограничивают доступ к сервису автоматически без проверки модератором.

## 9. Бизнес-правила

1. Один водитель не может выполнять две активные поездки одновременно.
2. Клиент не может оформить новую поездку, пока предыдущая активна (кроме заказа для
   члена семьи, если функция поддерживается).
3. Все изменения статусов поездки фиксируются в журнале событий.
4. Все финансовые операции должны быть атомарными и журналироваться.
5. Изменения тарифов вступают в силу по расписанию или немедленно — в зависимости от
   настроек администратора.
6. Архитектура должна предусматривать подключение новых типов услуг (доставка документов,
   корпоративные поездки, курьерская доставка) без переработки основных модулей.

## 12. Жизненный цикл и статусы поездки

### 12.1 Конечный автомат заказа (Order State Machine)
Все переходы статусов атомарны и фиксируются в журнале событий (см. §9, п.3).

```
CREATED            заказ создан клиентом
   │
   ▼
SEARCHING_DRIVER   идёт поиск свободного водителя
   │  ├─► NO_DRIVERS_FOUND ──► CANCELLED_SYSTEM
   ▼
DRIVER_ASSIGNED    водитель назначен (принял заказ)
   │
   ▼
DRIVER_EN_ROUTE    водитель едет к точке подачи
   │
   ▼
DRIVER_ARRIVED     водитель прибыл, ожидает клиента
   │
   ▼
IN_PROGRESS        поездка выполняется
   │
   ▼
COMPLETED          поездка завершена, ожидается оплата/оценка
   │
   ▼
CLOSED             оплата проведена, чек сформирован
```

**Терминальные статусы отмены:**
- `CANCELLED_BY_CLIENT` — отмена клиентом (до/после назначения, после прибытия, в пути — искл.);
- `CANCELLED_BY_DRIVER` — отмена водителем;
- `CANCELLED_SYSTEM` — нет доступных водителей / тайм-аут;
- `FAILED_PAYMENT` — сбой оплаты (с последующим retry и переходом в `CLOSED` или в спор).

### 12.2 Правила переходов
| Из статуса | Разрешённые переходы |
|-----------|----------------------|
| `CREATED` | `SEARCHING_DRIVER`, `CANCELLED_BY_CLIENT` |
| `SEARCHING_DRIVER` | `DRIVER_ASSIGNED`, `CANCELLED_BY_CLIENT`, `CANCELLED_SYSTEM` |
| `DRIVER_ASSIGNED` | `DRIVER_EN_ROUTE`, `CANCELLED_BY_CLIENT`, `CANCELLED_BY_DRIVER` |
| `DRIVER_EN_ROUTE` | `DRIVER_ARRIVED`, `CANCELLED_BY_CLIENT`, `CANCELLED_BY_DRIVER` |
| `DRIVER_ARRIVED` | `IN_PROGRESS`, `CANCELLED_BY_CLIENT`, `CANCELLED_BY_DRIVER` |
| `IN_PROGRESS` | `COMPLETED`, `CANCELLED_BY_CLIENT` (искл.), `CANCELLED_BY_DRIVER` (искл.) |
| `COMPLETED` | `CLOSED`, `FAILED_PAYMENT` |
| `FAILED_PAYMENT` | `CLOSED` |

### 12.3 Статусы водителя
`OFFLINE` → `ONLINE` (на линии) → `BUSY` (выполняет заказ) → `ONLINE`.
Водитель со статусом `PENDING_VERIFICATION` / `REJECTED` / `BLOCKED` не может выходить на линию.

## 13. Модель данных (основные сущности)

Ниже — логическая модель. Все таблицы содержат `id (UUID)`, `created_at`, `updated_at`;
регионально-зависимые сущности содержат `region_id` для мультирегиональности.

### 13.1 Пользователи и роли
- **User** — `phone`, `name`, `photo_url`, `role` (client/driver/operator/regional_admin/super_admin), `language`, `status`, `privacy_settings`, `notification_settings`.

## 15. Событийная модель и реальное время

### 15.1 WebSocket-каналы
- `client:{userId}` — статусы заказа, позиция водителя, уведомления;
- `driver:{driverId}` — новые заказы, отмены, сообщения;
- `order:{orderId}` — совместное отслеживание (клиент + семья + SOS-контакты).

### 15.2 Доменные события (event-driven)
`order.created`, `order.driver_assigned`, `order.status_changed`, `order.cancelled`,
`driver.location_updated`, `payment.completed`, `payment.failed`, `sos.activated`,
`document.verified`, `review.created`.

События публикуются в брокер сообщений (Kafka/RabbitMQ/NATS) и потребляются сервисами
уведомлений, аналитики и др. Гарантия доставки — **at-least-once** с идемпотентными
обработчиками.

### 15.3 Матчинг водителя
- геопространственный поиск ближайших свободных водителей (индекс: PostGIS / Redis GEO / H3);
- ранжирование по расстоянию, рейтингу, приоритету «избранных водителей»;
- тайм-аут ожидания принятия и переход к следующему кандидату;
- целевое среднее время назначения — до 30 секунд (KPI §10.1).

## 16. Пользовательские сценарии (Use Cases)

### UC-1. Заказ поездки клиентом
1. Клиент открывает главный экран, видит карту и своё местоположение.
2. Указывает пункт назначения (поиск/сохранённый адрес/точка на карте).
3. Система рассчитывает маршрут и стоимость, показывает тарифы.
4. Клиент выбирает тариф, способ оплаты, оставляет комментарий, подтверждает.
5. Система ищет и назначает водителя, показывает авто на карте в реальном времени.
6. Поездка выполняется; по завершении — оплата, чек, предложение оценить.

**Альтернативы:** нет водителей → уведомление и предложение повторить; отмена на любом
разрешённом шаге → применяется политика отмены региона.

### UC-2. Регистрация и верификация водителя
1. Создание аккаунта → анкета → загрузка документов → отправка на проверку.
2. Модератор/OCR проверяет документы → одобрение или отклонение с причиной.
3. После одобрения водитель выходит на линию и получает заказы.

### UC-3. Активация SOS
1. Клиент нажимает SOS во время поездки.
2. Экстренным контактам (до 5) отправляются ссылка на маршрут, координаты, данные
   водителя/авто, статус.
3. Событие фиксируется, оператор получает приоритетное уведомление.

### UC-4. Заказ для члена семьи
1. Клиент выбирает подтверждённого члена семьи как пассажира.
2. Поездка оплачивается со счёта заказчика; заказчик и пассажир получают отслеживание.

### UC-5. Управление регионом (админ)
1. Супер-админ создаёт регион/город, назначает регионального администратора.
2. Настраивает тарифы, комиссии, провайдеров, feature-флаги — **без изменения кода**.

## 18. Требования к надёжности и отказоустойчивости
- доступность инфраструктуры ≥ 99,9%, RTO ≤ 30 мин (KPI §10.1);
- отсутствие единой точки отказа: репликация БД (primary/replica), несколько инстансов сервисов;
- graceful degradation: при недоступности некритичных сервисов (аналитика, промокоды)
  основной сценарий заказа продолжает работать;
- circuit breaker, retry с экспоненциальной задержкой и таймауты для внешних вызовов;
- идемпотентность платёжных и статусных операций;
- регулярное резервное копирование БД и проверка восстановления (DR-план);
- health-checks и автоматический перезапуск нездоровых инстансов.

---

## 19. Требования к масштабированию (детально)
- **Горизонтальное масштабирование** stateless-сервисов за балансировщиком;
- **Мультирегиональность на уровне данных**: `region_id` во всех регионально-зависимых
  сущностях; возможность шардирования/партиционирования по региону;
- **Конфигурация через данные, а не код**: тарифы, комиссии, провайдеры, feature-флаги;
- **Асинхронная обработка** тяжёлых операций через очереди;
- **Кэширование** гео-поиска, тарифов, справочников;
- нагрузочное тестирование на пиковые сценарии перед запуском в новом регионе.

## 20. Безопасность и защита данных (детально)
- шифрование трафика (TLS 1.2+), шифрование чувствительных данных в покое;
- хранение документов водителей в приватном хранилище с ограниченным доступом;
- принцип наименьших привилегий (RBAC) для ролей и админ-панелей;
- изоляция данных регионов для региональных администраторов;
- защита OTP от перебора (лимиты, задержки, блокировки);
- аудит-лог действий администраторов и операторов;
- соответствие 152-ФЗ «О персональных данных»: согласие, право на удаление, минимизация;
- маскирование персональных данных в логах;
- регулярные проверки безопасности (SAST/DAST), управление секретами (Vault).

## 21. Наблюдаемость (Observability)
- **Метрики** (Prometheus): время назначения водителя, время отклика API, доля успешных

- **Трассировка** распределённая (OpenTelemetry);
- **Алёртинг** по KPI и критическим сбоям;

## 22. Тарификация и платежи
- расчёт стоимости до оформления заказа (прозрачность §2.2);
- компоненты тарифа: базовая подача + за км + за минуту + минимальная стоимость + surge;
- комиссия платформы настраивается по регионам;
- политика отмены и штрафов настраивается через админку без изменения кода (§8.12);
- поддержка нескольких платёжных провайдеров по регионам через адаптеры;
- атомарность и журналирование всех финансовых операций (§9, п.4), двойная запись (ledger);
- электронные чеки/квитанции для каждой поездки; вывод средств водителями.
