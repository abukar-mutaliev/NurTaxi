# Аудит безопасности проекта НУР (Nur Taxi)

- **Дата:** 31 августа 2026
- **Ветка:** `driver-app`
- **Область:** серверная часть (`server/`), мобильные приложения (`mobile/`), веб-панель админа (`web-admin/`), инфраструктура и конфигурация
- **Метод:** ручной анализ кода + проверка зависимостей (`npm audit`) + проверка боевого стенда `https://taxi.rulplus.ru`
- **Характер:** это внутренний технический аудит, а не пентест и не сертификационная проверка.

---

## 1. Итог одним абзацом

Кодовая база спроектирована с зрелым подходом к безопасности: JWT с ротацией refresh-токенов,
RBAC с изоляцией по регионам, шифрование ПДн в БД, маскирование ПДн в логах, аудит действий
администраторов, защита от IDOR, параметризованный SQL, `fail-fast` на слабой конфигурации в
production. **Главная проблема не в коде, а в развёртывании боевого стенда: сервер запущен
НЕ в режиме `production`**, из-за чего отключены все продовые проверки безопасности, а API
**отдаёт коды из SMS прямо в HTTP-ответе** — это позволяет войти под любым номером телефона
без доступа к самому телефону. Это блокирующая уязвимость (полный обход аутентификации на
текущем стенде). Остальное — управляемые задачи: уязвимые версии зависимостей, отсутствие
реального SMS-провайдера, отсутствие ограничения типа/размера файла при загрузке документов.

## 3. Что сделано правильно (сильные стороны)

Это важно зафиксировать: перечисленное ниже проверено по коду и работает.

- **JWT + ротация refresh.** `token.service.ts`: каждый refresh одноразовый (jti хранится в
  Redis и удаляется при использовании), повторное использование отклоняется — защита от кражи
  refresh-токена. Access-секрет и refresh-секрет разделены.
- **RBAC с изоляцией регионов.** `admin-scope.service.ts`: региональный админ и оператор видят
  только свой `region_id`; попытка обратиться к чужому региону → `403 REGION_FORBIDDEN`.
  Супер-админ — сквозной доступ. Проверки навешаны на все админ-контроллеры.
- **Защита от IDOR.** В заказах повсюду проверка владельца (`order.clientId !== userId` /
  `order.driverId !== driver.id` → `403`). Клиент не может прочитать чужой заказ по ID.
- **Шифрование ПДн в БД.** `field-encryption.ts`: AES-256-GCM для номера разрешения такси,
  региона выдачи и т.п. Ключ `FIELD_ENCRYPTION_KEY` обязателен в staging/production
  (иначе старт падает).
- **Маскирование ПДн в логах.** `pii-scrubber.ts` + pino `redact`: телефон, ФИО, адрес,
  дата рождения, госномер, VIN, ИНН, токены, пароли, коды — заменяются на `[REDACTED]`.
- **Аудит администраторов.** `admin-audit.interceptor.ts` логирует все мутации в админке;
  плюс мониторинг массового чтения ПДн (`mass-read-monitor`) с порогом — след для 580-ФЗ.
- **`fail-fast` на слабой конфигурации.** `production-security.ts`: в staging/production старт
  отклоняется при дефолтных JWT-секретах, дефолтном пароле БД, `DB_SSL != true`, CORS с `*` или
  пустым, отсутствии ключа шифрования, зарубежной зоне S3.
- **Rate-limiting OTP.** `@Throttle` 3 запроса кода/мин + собственный cooldown в Redis (проверено
  на боевом стенде — работает). Защита от перебора кодов (`maxVerifyAttempts = 5`).
- **Хранение токенов на мобильных.** `expo-secure-store` (Keychain/Keystore),
  `WHEN_UNLOCKED_THIS_DEVICE_ONLY`; access-токен только в памяти. НЕ AsyncStorage.
- **Web-admin.** Access-токен в памяти, refresh в `sessionStorage` (не `localStorage`),
  XSS-стоков (`dangerouslySetInnerHTML`, `eval`) нет.
- **SQL.** Параметризованные запросы TypeORM; единичные интерполяции (`${col}`,
  `${OrderStatus.*}`) — из белого списка/констант, не из пользовательского ввода. Инъекций нет.
- **Secrets в git.** `.env` файлы под `.gitignore`, в репозитории только `.env.example`.

## 4. Детали находок

### 🔴 C-1. Боевой сервер не в режиме production → обход аутентификации

**Что нашли.** Прямой запрос к боевому стенду:

```
POST https://taxi.rulplus.ru/api/v1/auth/otp/request  {"phone":"+7..."}
→ {"expiresInSec":300,"resendAfterSec":60,"devCode":"9430"}
```

Поле `devCode` — это код из SMS. Он возвращается в ответе только когда `NODE_ENV != production`
(см. `otp.service.ts`: `devCode: process.env.NODE_ENV === 'production' ? undefined : code`).

**Чем опасно.**
1. **Полный обход аутентификации.** Любой человек запрашивает код на чужой номер, получает его
   в том же ответе, подтверждает — и входит в аккаунт без доступа к телефону жертвы. Работает для
   любой роли, включая администраторов.
2. **Каскад.** Раз `NODE_ENV != production`, значит и `assertProductionSecurity` не выполняется.
   Следовательно на стенде **могут быть активны**: дефолтные JWT-секреты (подделка токенов),
   дефолтный пароль БД, выключенный TLS к БД, CORS `*`, отсутствующий ключ шифрования ПДн,
   stub-SMS. То есть одна неверная переменная окружения снимает сразу весь продовый контур защиты.

**Как проверить.** На сервере: `echo $NODE_ENV` (должно быть `production` либо `staging`).

**Как исправить.**
- Выставить `NODE_ENV=production` (или `staging`) в окружении боевого сервиса и перезапустить.
- После рестарта сервис сам откажется стартовать, если какой-либо секрет остался дефолтным —
  это и есть штатная проверка. Все проблемы из «каскада» закрываются заданием реальных значений:
  `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET`, `DB_PASSWORD`, `DB_SSL=true`, `CORS_ORIGINS`,
  `FIELD_ENCRYPTION_KEY` (≥32 симв.), `S3_REGION=ru-*`.
- Повторно выполнить запрос `otp/request` и убедиться, что `devCode` больше **не** возвращается.

### 🔴 C-2. Нет реального SMS-провайдера

**Что нашли.** В `server/src/modules/auth/sms/` только `stub-sms.provider.ts`. Реальный код в
production не отправляется (stub при `NODE_ENV=production` просто пишет ошибку в лог и выходит).

**Чем опасно.** После исправления C-1 (когда `devCode` перестанет возвращаться) вход вообще
перестанет работать — код никуда не придёт. То есть C-1 и C-2 нужно закрывать **вместе**: как
только выключаем утечку кода, сразу должен работать настоящий канал доставки SMS. До этого
второго фактора аутентификации фактически нет.

**Как исправить.** Реализовать провайдер под интерфейс `SmsProvider` (например SMS Aero / SMS.ru
/ оператор с российскими серверами — важно для 580-ФЗ) и включить его по конфигу региона.

### 🟠 H-1. Уязвимые prod-зависимости сервера

`npm audit --omit=dev`: **9 high, 56 moderate** (critical нет). Значимые:

| Пакет | Проблема |
|-------|----------|
| `multer` | DoS через незавершённую обработку составных запросов |
| `lodash` | Code injection через `_.template` |
| `js-yaml` | Prototype pollution в merge (`<<`) |
| `brace-expansion` | DoS (неограниченное расширение → OOM) |
| `@opentelemetry/*`, `@nestjs/platform-express` | транзитивные high |

**Как исправить.** `cd server && npm audit fix`; что не закрылось автоматически — обновить
вручную/через `overrides`. `multer` актуален, если где-то используется загрузка multipart —
проверить и обновить в первую очередь.

---

### 🟠 H-2. Уязвимые зависимости мобильных приложений

`npm audit` (mobile): **1 critical + 10 high**. Critical — `handlebars` (JS injection), но он
приходит транзитивно через `eslint-plugin-boundaries` — это **инструмент сборки/линтинга, в
бандл приложения не попадает**. Большинство high — тоже сборочные (`metro`, `image-size`,
`nanoid`, `js-yaml`). Прямого влияния на устанавливаемое приложение почти нет, но гигиену
восстановить нужно.

**Как исправить.** `cd mobile && npm audit fix`; отдельно оценить рантаймовые (если `nanoid`
используется в самом приложении — обновить). Сборочные — обновить при плановом апдейте toolchain.

---

### 🟡 M-1. Загрузка документов: нет белого списка типов и лимита размера

**Что нашли.** `PresignDocumentDto.contentType` — это `@IsString()` без ограничения значений, а
размер файла нигде не задаётся. Presigned-URL выдаётся под произвольный `Content-Type`.

**Чем опасно.** Водитель (авторизованный) может загрузить в приватный бакет файл любого типа и
размера — вектор для хранения нежелательного контента и раздувания хранилища. Риск ограничен тем,
что бакет приватный и ключ привязан к владельцу (`storageKey` проверяется на `drivers/{id}/`).

**Как исправить.** Ограничить `contentType` белым списком (`image/jpeg`, `image/png`,
`application/pdf`) через `@IsIn([...])` и задать в presigned-URL условие на размер
(`Content-Length` range) и на content-type.

---

### 🟡 M-2. Дефолтные секреты молча работают в dev

**Что нашли.** `configuration.ts`: `JWT_ACCESS_SECRET ?? 'change-me-access-secret'`,
`DB_PASSWORD ?? 'nurtaxi'`, `S3_SECRET_KEY ?? 'nurtaxi123'` и т.п. `assertProductionSecurity`
ловит их только при `NODE_ENV=production|staging`.

**Чем опасно.** Само по себе для локальной разработки — норма. Опасно **в связке с C-1**: если
боевой стенд идёт как `development`, эти дефолты становятся боевыми. Отдельного действия сверх
исправления C-1 не требует — но подтверждает, насколько важно правильно выставить `NODE_ENV`.

---

### 🟢 L-1. Web-admin: 1 high-зависимость

`brace-expansion` (транзитивно, DoS). Низкий приоритет. `npm audit fix` при плановом апдейте.

### 🟢 L-2. CI: нет отдельного сканера секретов и SAST

В `.github/workflows` есть Trivy (сканирование образов/зависимостей) — это хорошо. Желательно
добавить: сканер секретов (gitleaks/trufflehog) на pre-commit и в CI, а также SAST
(например, Semgrep) для регулярной проверки кода.
